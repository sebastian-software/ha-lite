# ADR 0015: Follow the Sebastian Software repository conventions

- Status: Accepted

## Context

ha-lite was seeded from a squashed import of `home-assistant/core`, so it
inherited that project's governance along with its code: a contributor licence
agreement, an AI policy, a contributing guide, a funding link, issue forms, a
pull-request template, a generated `CODEOWNERS`, and a second copy of the agent
instructions generated for GitHub Copilot.

None of it describes this repository. `CLA.md` says a contribution is signed by
opening a pull request "to a repository under the Home Assistant organization".
`CONTRIBUTING.md` tells the reader to fork `home-assistant/core` and target its
`dev` branch. `FUNDING.yml` collects for the Open Home Foundation. `CODEOWNERS`
requests review from `@home-assistant/*` teams that do not exist here, and is
regenerated by hassfest from integration manifests, so it grows back on its own.
The pull-request template asks the author to confirm they reviewed two other
open pull requests in a repository this one is not.

The effect is not merely cosmetic. The template's checklist encodes upstream's
contribution rules, so every pull request opened here presented a checkbox — "I
understand the code I am submitting and can explain how it works" — that belongs
to a review process this repository does not run. Inherited governance that
nobody applies still shapes what contributors and agents do.

`AI_POLICY.md` is the sharpest case. It states that autonomous agents may not be
used to contribute and that such pull requests will be closed. That is a
reasonable rule for a project with volunteer maintainers reviewing contributions
from strangers. It is the opposite of how this repository works: ha-lite is
developed by its owner together with coding agents, under that owner's review.
Carrying upstream's rule meant the repository's own instructions forbade the way
it is actually built.

Sebastian Software already answers all of this once, for every repository, in
`sebastian-software/standards`. Its `common` scope defines the security policy,
code of conduct, support guide, code owners, issue forms and pull-request
template, and settles that `AGENTS.md` is the canonical agent file.

## Decision

Follow the Sebastian Software conventions, and delete what neither they nor this
repository need.

The community baseline comes from `sebastian-software/standards`
(`reference/common/*`), adapted where this repository differs: the security
contact link points at this repository's advisory form, `SECURITY.md` says that
a defect reproducing on upstream Home Assistant belongs to `home-assistant/core`,
and the pull-request template's Validation section names the commands this
project actually runs.

`AGENTS.md` is the only agent instruction file. `CLAUDE.md` is a symlink to it —
the convention asks for a one-line `@AGENTS.md` pointer, and a symlink is the
same answer with one less file to keep in sync. The generated
`.github/copilot-instructions.md`, its generator and its pre-commit hook are
gone: a second rendering of the same guidance is a file that can disagree with
its source.

Upstream governance is deleted rather than adapted, because adapting it would
mean maintaining a fork of somebody else's rules. That covers `AI_POLICY.md`,
`CLA.md`, `CONTRIBUTING.md`, `FUNDING.yml`, the generated `CODEOWNERS` with its
hassfest plugin, `codecov.yml`, `README.rst` and its screenshots, and the
agentic-workflow action lock. Dependabot goes too: Renovate is configured here
and now covers GitHub Actions as well, so one tool proposes dependency updates
instead of two.

## Consequences

A contributor reads rules that apply to this repository. An agent reads one file
rather than three, and that file no longer forbids the way the project is built.

Deleting `CODEOWNERS` needed the hassfest plugin that regenerates it to go as
well, which is upstream surgery of the kind ADR 0014 warns about. It is the
minimum the deletion needs — two import lines and the plugin file — and without
it the file returns on the next hassfest run. Manifest-level `codeowners`
validation is untouched.

This repository is not managed by the `standards` CLI, which targets Node and
Rust projects. The common files were copied once and are now owned here, so a
later change upstream in `standards` does not reach them automatically; that is
the same trade the CLI makes for seeded files.

The issue forms label with `type:bug`, `type:feature` and `question` from the
org-wide taxonomy. Those labels are not created by this change, and applying the
taxonomy to the repository's existing labels is still open.
